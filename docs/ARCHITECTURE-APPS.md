# MoodBook — архітектура екосистеми «сайт + iOS + Android» (чернетка, 5 вересня 2026)

> **Статус 5 вересня 2026:** апки на паузі. Пріоритет: довести сайт до ідеалу і підключити платіжку (Stripe або WayForPay, плюс PayPal). Коли платіжка вирішена — першим робимо Google Play (простіший реліз), Apple відкладено на невизначений час.

Мета: одна людина, один акаунт, одна підписка. Оплатив на сайті — має Pro в апці. Оплатив в апці через Apple чи Google — має Pro на сайті.

## 1. Головна ідея за 30 секунд

```
                 ┌──────────────────────────────┐
                 │  Supabase (спільний бекенд)   │
                 │  auth · users · entitlements  │
                 │  shelf · liked_tracks         │
                 └───────┬──────────┬───────────┘
        ┌────────────────┘          └───────────────┐
        │                                            │
┌───────┴────────┐   ┌────────────────┐   ┌──────────┴──────────┐
│  Сайт (Vercel) │   │  api/ (Vercel) │   │ Апки iOS + Android  │
│  index.html    │   │ analyze/books/ │   │ Capacitor-оболонка  │
│  js/app.js     │   │ search/health  │   │ навколо тих самих   │
│                │   │ + billing/*    │   │ index.html/app.js   │
└───────┬────────┘   └───────┬────────┘   └──────────┬──────────┘
        │                    │                        │
   WayForPay             вебхуки від              App Store IAP
   (оплата на сайті)   WayForPay/Apple/Google      Google Play Billing
```

- **Один код інтерфейсу.** Апки — це наш сайт, загорнутий у Capacitor (WebView + нативні плагіни). Ніякого React Native чи Swift/Kotlin з нуля. Vanilla JS лишається.
- **Одне джерело правди про підписку** — таблиця `entitlements` у Supabase. Сайт і апки лише запитують «чи цей користувач Pro?». Хто саме взяв гроші (WayForPay, Apple чи Google) — деталь.
- **Акаунт обов'язковий для Pro.** Без входу неможливо впізнати людину між пристроями. Free лишається без реєстрації, як зараз.

## 2. Що з чим з'єднується

### 2.1 Supabase (уже в roadmap)
Таблиці:
- `profiles` — id (= auth user), email, created_at.
- `entitlements` — user_id, plan (`pro`), source (`wayforpay` | `apple` | `google` | `promo`), status (`active` | `grace` | `expired`), expires_at, external_id (номер підписки в магазині), updated_at. **Одна активна на користувача.**
- `shelf`, `liked_tracks` — те, що зараз лежить у localStorage (`mb_books`, `mb_liked_tracks`), з міграцією при першому вході.
- `promo_codes` — код, ліміт використань, тривалість.

Row Level Security: користувач читає лише свої рядки; писати в `entitlements` може лише сервер (service key у Vercel env).

### 2.2 Нові serverless-функції у `api/billing/`
- `POST /api/billing/wayforpay/webhook` — WayForPay повідомляє про оплату/продовження/скасування → створюємо чи продовжуємо entitlement `source=wayforpay`.
- `POST /api/billing/apple/notify` — App Store Server Notifications v2 (підписка куплена, продовжена, скасована, повернення грошей) → те саме з `source=apple`.
- `POST /api/billing/google/notify` — Google Real-Time Developer Notifications через Pub/Sub → `source=google`.
- `POST /api/billing/verify` — апка після покупки надсилає чек, сервер перевіряє його в Apple/Google і вмикає Pro одразу, не чекаючи вебхука.
- `GET /api/me` — повертає профіль + актуальний entitlement. Сайт і апки викликають це при старті й після покупки.

Усі магазинні ключі (Apple .p8, Google service account) — тільки в Vercel env.

### 2.3 Сайт
- Кнопка «Go Pro» → якщо не залогінений, спочатку вхід (magic link на email через Supabase, без паролів) → WayForPay.
- `isPro()` у `js/app.js` перестає читати лише `mb_pro` і починає читати `/api/me` (з кешем у localStorage на випадок офлайну). Промокоди й `?pro=1` лишаються як тестові механізми.

### 2.4 Апки (Capacitor)
- Один репозиторій. `npx cap add ios` / `npx cap add android` створюють папки `ios/` і `android/`, у які копіюється наш `index.html`, `css/`, `js/`, `assets/`. API-виклики йдуть на `https://moodbook.ink/api/...` (потім moodbook.ink).
- Плагіни, які реально потрібні: In-App Purchases (див. 3), Browser/Share (поділитися книгою), Preferences (заміна localStorage), Keep Awake (не гасити екран під час читання).
- Вхід у той самий Supabase-акаунт, що й на сайті.

## 3. Оплата: правила магазинів, які не обійти

- **Купівля Pro всередині апки — тільки через Apple/Google IAP.** Показати в апці кнопку «оплати карткою на сайті» Apple забороняє в більшості країн (у США і ЄС правила м'якші, але це окремі налаштування; на старті простіше не ризикувати).
- **Купив на сайті — користуйся в апці: дозволено.** Це офіційно описано як «multiplatform services»: апка мусить сама теж продавати Pro через IAP, але може визнавати підписку, куплену деінде. Саме це нам і треба.
- **Комісія:** Apple і Google по 15 % (програма для малого бізнесу до $1 млн/рік). WayForPay на сайті — близько 2–3 %. Тобто вигідніше, коли люди платять на сайті; апка — для зручності й видимості в магазинах.
- **Виплати від Apple/Google потребують юридичної особи або ФОП і банківського рахунку.** Це той самий блокер, що й у WayForPay. Без ФОП можна розробляти й тестувати, але не продавати.
- **Ціни в магазинах задаються окремо** ($9.99/міс і $99.99/рік уже ухвалено; Apple округлить під свої цінові рівні).

**RevenueCat чи власна реалізація?** Рекомендація — **RevenueCat** (безкоштовно до $2.5k/міс виторгу). Він приймає чеки від обох магазинів, слухає їхні вебхуки, тримає статус підписки й шле нам один зрозумілий вебхук. Це прибирає найболючішу частину (перевірка чеків Apple/Google, grace-периоди, повернення). Оплату з сайту через WayForPay RevenueCat не знає, тому для неї пишемо свій маленький вебхук, і в `entitlements` обидва джерела сходяться.

## 4. Один акаунт між сайтом і апкою

1. Людина реєструється (email + magic link або «Увійти з Apple/Google»). Apple вимагає кнопку «Sign in with Apple», якщо є інші соцвходи — тож даємо email-посилання + Apple + Google.
2. Після входу сайт/апка кличе `/api/me` → отримує `pro: true/false`.
3. Купила на сайті → WayForPay → вебхук → entitlement → наступний `/api/me` в апці показує Pro (апка перевіряє при старті й після повернення з фону).
4. Купила в апці → IAP → RevenueCat → вебхук → entitlement → сайт показує Pro після оновлення сторінки.
5. Скасувала → джерело повідомляє → `status=expired` після кінця сплаченого періоду. Доступ живе до `expires_at`, як і має бути.

## 5. Ризики, про які треба знати ДО старту

- **YouTube у фоні.** Наш плеєр — офіційний YouTube-плеєр. У мобільній апці він грає лише поки апка на екрані; фонове відтворення YouTube забороняє (це порушення умов і технічно iOS ставить відео на паузу). Для читача паперової книги це означає: телефон лежить із увімкненим екраном (плагін Keep Awake допоможе, але батарея). Це головний продуктовий ризик апки. Варіанти на майбутнє: ліцензована музична бібліотека (Epidemic Sound, Artlist API), Spotify/Apple Music інтеграція (плейлисти відкриваються в їхніх апках), або власний каталог від інді-композиторів.
- **Apple guideline 4.2 «мінімальна функціональність».** Апку, яка є просто сайтом у WebView, можуть відхилити. Треба 2–3 нативні речі: офлайн-полиця, «продовжити читати» з останньою книгою, віджет/нотифікація «час читати», поділитися Reading Card. Це збігається з roadmap.
- **Вартість і акаунти:** Apple Developer $99/рік, Google Play $25 одноразово, Mac потрібен для збірки iOS (або хмарна збірка Codemagic/Ionic Appflow за ~$30–100/міс).
- **Терміни огляду:** перша публікація в App Store — від кількох днів до пари тижнів із можливими відхиленнями.

## 7. Що НЕ змінюється
- Vanilla JS, без фреймворків. Capacitor не змушує нічого переписувати.
- Serverless у `api/`, ключі лише в env.
- Ціни та free-ліміт (3 пошуки на день) — як ухвалено.
- Ключі localStorage `mb_*` лишаються для Free-користувачів і як офлайн-кеш.
